## DB·스키마

**observations 테이블**  
- **추천: 만든다.**  
- 성능: TFT 학습·추론 입력은 A 파이프라인이면 되지만, API에서 “과거 24h 실측 곡선”을 안정적으로 주려면 DB에 두는 편이 데이터 일관성에 유리합니다.  
- 지연: 한 번에 조회·인덱스(`station_id`, `datetime`)로 응답이 단순해집니다.  
- 비용: 행 수만 관리하면 PostgreSQL 한 인스턴스로 부담은 보통 작습니다.

**rainfall 테이블**  
- **추천: UI에 “강수량 시계열”이 꼭 필요할 때만.** 없으면 테이블·적재 파이프라인을 줄여 비용·일정을 아낍니다.  
- 성능: 모델은 A 쪽에서 이미 강수 피처를 쓰면 되고, DB 테이블 유무가 **모델 정확도**와 직접 연결되진 않습니다.

**predictions row 구조 (horizon별 row vs 한 row)**  
- **추천: “한 관측소·한 `predicted_at`당 1 row + horizon별 컬럼 또는 JSONB” 쪽이 유리한 경우가 많음.**  
- 지연: `GET .../predictions` 한 번에 1~6h 전부 내려줄 때 **행 1개(또는 소수)** 조회가 유리합니다.  
- 비용: row 수가 줄어 인덱스·VACUUM 부담이 약간 줄 수 있습니다.  
- (정규화 “horizon당 1 row”는 분석·부분 업데이트에는 좋지만, 지금 API 형태와 맞추려면 조인/다건 조회가 늘 수 있습니다.)

## 백엔드·배포·스택

**FastAPI**  
- **추천: 확정.** 비동기·타입 힌트·Python 생태계와 A 연동 모두 지연·개발 속도에 유리합니다.

**PostgreSQL**  
- **추천: 확정.** 시계열 메타·예측 결과·관측 적재에 무난하고, 운영 복잡도 대비 신뢰도가 좋습니다.

**배포(ngrok 등)**  
- **추천: 4일짜리 데모·합숙이면 ngrok 유지.**  
- 성능: **모델 추론 품질과는 무관**합니다.  
- 지연: 터널·지역에 따라 약간 들쭉날쭉할 수 있어 “체감 latency”는 클라우드 고정 엔드포인트보다 불리할 수 있습니다.  
- 비용: 가장 낮은 축.  
- 정리: **비용·기한 우선이면 ngrok**, 나중에 여유 있으면 같은 API를 고정 URL로만 옮기면 됩니다.

## 예측 주기·전달

**배치 vs 실시간**  
- **추천: 배치(예: 1시간마다 전 관측소 일괄 추론).**  
- 성능: TFT는 보통 **윈도우 단위 배치 추론**이 안정적이고, GPU/CPU 활용도 좋습니다.  
- 지연: “최신 데이터 반영”은 배치 주기만큼 늦지만, **요청마다 모델 돌리는 것**보다 API p95는 예측 가능하고 낮게 유지하기 쉽습니다.  
- 비용: 실시간 대비 **프로세스·스케일링 부담이 훨씬 작습니다.**

**A→B 파일 형식 (JSON vs CSV)**  
- **추천: JSON.**  
- 성능: 모델 자체와 무관하지만, **quantile·horizon 중첩 구조**를 실수 없이 넘기기 좋습니다.  
- 지연/비용: 파싱·검증 파이프가 단순해져 통합 이슈가 줄어 **간접적으로** 지연·인건비를 줄입니다.

**신뢰구간(0.1 / 0.5 / 0.9) 제공**  
- **추천: 제공한다(TFT가 이미 quantile을 쓰는 설정이면 특히).**  
- 성능: **학습·추론 파이프라인은 그대로**이고, 출력만 추가하는 수준이면 정확도 트레이드오프는 거의 없습니다.  
- 지연: 응답 payload만 커짐 → horizon 6개 수준이면 체감 지연은 보통 미미합니다.

## 신호등·프론트·B↔C

**신호등 계산 위치 (B vs C)**  
- **추천: B에서 계산해 `status`로 내려준다.**  
- 성능: 예측값과 임계값 비교는 **모델 성능과 무관**하지만, **정책 단일화**로 “같은 데이터인데 화면마다 색이 다름” 버그를 막습니다.  
- 지연: 비교 연산 비용은 무시 수준입니다.  
- 비용: B CPU 소폭 증가, 무시 가능.

**업데이트 주기 (1시간 배치 vs 고정 결과)**  
- **추천: 예측 배치 주기와 맞춘 “1시간 단위 갱신”을 기본.**  
- 성능: 모델은 배치와 정합됩니다.  
- 지연: 사용자는 “최대 1시간 지연”으로 이해하면 됩니다.  
- 비용: 폴링·재계산 횟수가 줄어 클라이언트·서버 모두 유리합니다.

**CORS(localhost)**  
- **추천: 개발 단계에서는 localhost 명시 허용**, 배포 URL 정해지면 그 origin만 추가.  
- 성능·비용과 무관, 통합 필수 설정입니다.

## A 쪽 확인 사항(데이터)

**lat/lng, alert_level / warning_level**  
- **추천: 문서대로 A가 “있는지” 즉시 확인하고, 없으면 `stations` 시드·외부 공개 메타로 보강하는 합의를 Day 1에 박기.**

- 지연·비용: 사전에 스키마·시드 확정이 되어야 B/C Mock이 안 흔들립니다.
